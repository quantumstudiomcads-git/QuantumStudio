# Quantum Studio Licence Manager architecture

The Licence Manager is an operator-only PySide6 desktop application launched with `scripts/run_licence_manager.py`. It is outside the customer frontend, has no network listener or public API, and is excluded from the customer bundle. Its beta bridge pulls application records and explicitly pushes review status to the website; the local manager remains authoritative for operator decisions.

## Trust domains

1. The public website collects applications, exposes a versioned read-only application export, and accepts a narrowly scoped authenticated review-status mirror update. Website status is a mirror only and never authorizes an operator decision or signing.
2. The local manager encrypts applicant data, records review decisions, imports device activation requests, derives allowlisted profiles from the canonical calculation catalogue/backend registry, records issuance metadata, and requests a signature through a local authority interface.
3. The local licence authority is a separate Ed25519 domain (`lic-` key IDs in production). Its only production issuance entry point accepts an application ID, activation-request ID, named profile, and explicit confirmation. It reloads and checks authoritative database rows, derives all signed fields from policy and those rows, then loads the DPAPI-protected signing key and signs inside the same SQLite transaction as the issuance, transition, and audit records. No supported generic DPAPI-unprotect API exists; the authority accepts a protected signing-key envelope only from its configured file. The general-purpose client lease helper is not exposed as the production authority API. Tests use an explicitly injected, in-memory TEST ONLY signer; production mode never falls back to it. There is no production key ceremony or automatic production signing-key generation. Updater signing remains independent.

This is an in-process application boundary: imported data cannot directly choose signed claims, and supported manager code has no production API for arbitrary-payload signing or arbitrary DPAPI decryption. Signing and applicant-data keys use distinct version-1 purpose-bound envelopes (`licence-signing-ed25519` and `applicant-pii-database-key`). Python privacy conventions do not isolate code within the process. Arbitrary code execution as the same Windows user can call Windows DPAPI directly and defeats this boundary.

The Website → Licence Manager applicant pull is read-only and imports the fetched schema-version-1 payload through the same strict `import_applicants_json` validation used by manual JSON import. The client uses `QS_OPERATOR_WEBSITE_URL` and `QS_OPERATOR_SYNC_TOKEN`; the website endpoint reads the separate bearer-token secret `OPERATOR_SYNC_TOKEN`. Local HTTP is allowed only for an explicitly local/test run and loopback address; production sync requires HTTPS. The importer assigns imported rows the local `APPLIED` state and ignores website review/licence state for local decisions.

The explicit Licence Manager → Website status push mirrors only `APPLIED`, `UNDER_REVIEW`, `APPROVED`, and `REJECTED`. Local SQLite is re-read immediately before the push and remains the source of truth. The write endpoint accepts only a version-1 status body, validates the existing website workflow transition, conditionally updates the expected D1 state, and appends a controlled `OPERATOR_STATUS_SYNC` event. Retries already reflected in D1 succeed without a duplicate transition audit; concurrent unexpected status changes fail with conflict. This write capability uses the distinct `QS_OPERATOR_STATUS_SYNC_TOKEN` / Cloudflare `OPERATOR_STATUS_SYNC_TOKEN` bearer credential, never the read-only token. Local status decisions are not rolled back when the website is unavailable; the UI reports the mirror stale and permits an explicit retry.

Authenticated website users can read their own beta application's public status through `GET /api/beta/me`. New submissions store the authenticated `users.user_id` in the nullable `beta_applications.user_id` foreign key; a partial unique index prevents a second application for the same user until reapplication is explicitly designed. The endpoint returns only application ID, status, and submission/update timestamps. Existing rows with a null user ID are not linked by email and will remain unavailable to the account status view unless associated through a future reviewed process or an explicit test fixture.

Licence issuance/revocation metadata sync and activation-request sync are not implemented. Signing remains entirely local. The production Cloudflare secrets and deployment are not configured.

Production authority status is metadata-only: it checks metadata syntax and public-key encoding plus protected-blob file presence. A present protected blob is reported as unverified, never as ready or currently valid. Startup, refresh, review, imports, and profile selection do not decrypt the licence key. The normal production DPAPI-unprotect path is reached only after issuance authorization and request/device/policy validation have been repeated inside `BEGIN IMMEDIATE`. Private-key references are released immediately after signing and are not cached on the authority object. Python cannot guarantee complete memory zeroization; process or Windows-account compromise defeats this boundary. A last-use success shown during the running manager session is historical evidence and does not verify the current protected blob.

The existing client licence verifier authenticates canonical JSON envelopes and device binding. The manager retains that schema and adds policy metadata as signed fields. It supplies explicit entitlement lists; it does not use wildcard grants. A request's `requested_profile` is never authorization: the operator makes a separate audited local profile decision before issuance.

## Data and PII

Production SQLite and the DPAPI-wrapped data key live beneath `%LOCALAPPDATA%\QuantumStudio\LicenceManager`. Applicant fields are serialized as a version-1 AES-256-GCM envelope. AAD binds the application identifier, SQLite schema version, applicant table, record ID, field, and encryption format version. The email lookup index is a keyed HMAC derived from a separately domain-separated data key. Email identity is trimmed, NFC-normalized, case-folded, and NFC-normalized again; no provider-specific rewriting is done. Duplicate normalized email identities are rejected pending a reviewed reapplication workflow. This keyed index is equality protection, not anonymization: compromise of its key enables offline guessing of likely email addresses. Audit details contain opaque IDs and controlled reason codes rather than PII. Private licence signing keys are never stored in SQLite.

Production storage is opened only by a central database/key-pair bootstrap. It takes a bounded cross-process initialization lock before evaluating state, then rechecks all storage paths while holding the lock. On Windows the lock is an exclusively opened per-root file with read, write, and delete sharing denied; the operating system releases the handle if its process exits unexpectedly, and the next process validates the pending state before recovery. First run is allowed only when both database and key are absent; a strict, versioned, root-bound pending marker records the initialization operation and opaque random generation UUID before key publication. The UUID is authenticated inside the versioned PII-key envelope and stored as non-secret database metadata. The database writes its generation UUID, version-1 initialization-complete metadata, and initial schema migrations in the same transaction. An existing database is recoverable only when its own metadata contains a canonical matching UUID, valid version-1 completion state, and the complete current schema migration set. The pending marker is recovery coordination data, not proof that an existing database belongs to the operation. An existing database without valid pairing and completion metadata is never adopted, migrated, or relabeled; unprovable partial initialization fails closed with the database, key, and marker preserved for manual inspection or matched-backup restoration. A database with a missing key is never treated as disposable, including when it has no applicant rows.

Windows CurrentUser DPAPI ties access to the Windows user account. It does not protect data after that account or session is compromised. Same-user arbitrary code can invoke Windows DPAPI directly; the manager boundary limits supported APIs, imported data, and UI paths, not a compromised process or unlocked session. A workstation backup must protect the encrypted database and DPAPI-wrapped data key together. Restoring them under a different Windows account may not be possible. No production signing key, signing-key ceremony, or production database migration has been performed.

Unsupported operating systems fail closed for production storage and signing. Tests inject a test-only data key and ephemeral signer. Test fixtures use reserved `example.test` addresses only.

## Audit and revocation

Audit events use canonical serialization and a SHA-256 previous-event chain. Verification detects ordinary changes to rows or ordering and removed middle events. Without an external trusted checkpoint, deleting the tail, replacing the complete chain and recomputing it, or restoring an older database snapshot cannot be proven. A hash chain is tamper evidence, not append-only immutability.

Revocation records the operator's local administrative decision. A delivered offline licence remains usable until its signed expiry unless a later authenticated client refresh/revocation mechanism is implemented. Current controls are 90-day expiry, device binding, controlled renewal, operator audit, and no automatic transfer.

## Customer package boundary

Windows and Linux package audits reject forbidden paths and known sensitive content independently of filename extensions. The authoritative Windows build writes a canonical, versioned `quantumstudio-payload-inventory.json` after the payload and both metadata files are final. It records the exact relative path, byte size, and SHA-256 of every other payload file. The installer rejects legacy bundles without this inventory, checks metadata consistency and the exact file set, streams hashes, performs content-sensitive checks, then rechecks before ISCC. SQLite database/journal/WAL signatures, PEM private-key material, manager protected-key markers and known operator records, receipts, and pre-issued licences are rejected. Recognized archive/container formats are forbidden rather than unpacked. Linux AppImage staging reuses the content-sensitive audit but does not yet use the Windows inventory format.

This detects known formats and verifies the inventoried bundle; it cannot classify every possible encrypted or arbitrary byte sequence. Clean source and build-host controls remain part of the release trust boundary. These checks and focused tests do not prove safety from a completed customer build. The customer front end does not import this package. The manager remains excluded from customer Nuitka bundles, installers, AppImages, update manifests, release ZIPs, Engine Packs, and website builds.
