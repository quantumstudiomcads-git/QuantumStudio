# W5 Managed Scientific Runtime Audit

## Scope

W5 implements offline Engine Pack integrity and activation policy, verified runtime tool mapping, declared streaming stage-in/stage-out contracts, and runtime-agent task-control primitives. It is execution infrastructure only: no QE, EPW, Wannier90, BoltzTraP2, Bader, scientific writer, parser, ResultStore, calculation intent, or `.qs` schema was changed.

## Engine Pack contract

A local Engine Pack root contains `engine-pack.json` schema `1`, a version, Linux platform/architecture identity, and per-tool relative paths with SHA-256. The caller supplies the expected manifest digest. Source validation occurs before install. The fixed agent streams each declared pack file into its engine-only `.staging` root, verifies the staged manifest and files again, then performs atomic activation. The managed target is versioned under `/opt/quantumstudio/engines/packs/` conceptually, with `active.json` as an atomically replaced active record. Ownership metadata protects unknown roots. Same version/different hash is a conflict; a lower version never silently replaces an active pack; old packs remain available for rollback.

Manifest-declared logical tool IDs, not filename or PATH searching, map to absolute runtime paths. Existing `EngineFamily` is reused as the family/provenance model. Coherent QE/EPW/Wannier version metadata stays manifest-owned; W5 does not invent engine combinations.

## Files and task control

Host paths and runtime paths remain different namespaces. Declared `StageInArtifact` and `StageOutArtifact` objects are the only transfer units. Transfer is binary streaming, not JSON/base64; critical writes use temporary files, optional SHA verification, fsync where applicable, and atomic replace. Agent containment permits only approved managed working/pseudo/engine-staging roots and rejects traversal, NUL, Windows-style runtime paths, and symlink escape. Scratch, wavefunctions, `.save`, `_ph0`, and `epmatwp` are retained runtime-side unless separately declared.

The agent exposes only `run`, `stage-in`, `stage-out`, `status`, and `cancel`. It is not a shell. Its durable task record is keyed by a validated task ID and stores PID/PGID plus a process-start discriminator. `cancel` resolves that owned record, sends SIGTERM to the process group, waits a bounded grace interval, and uses SIGKILL only if needed. Arbitrary PID killing and user-distro targeting are impossible through these APIs.

## Result boundary and readiness

The W5 adapter starts after existing compiler generation. It stages compiler-generated bytes unchanged, resolves a verified logical tool, uses the existing W4 bridge, and collects declared host parser/log files. `ResultService` is called with the host workflow root only; it never receives a runtime POSIX path. Engine exit success and parser validity remain separate existing concepts.

Scientific readiness requires exact managed WSL2 registration, W3 metadata, W4 compatible agent, verified Engine Pack manifest/platform/architecture/files, available logical tools, and writable managed workflow storage. Optional missing tools remain capability failures rather than a misleading global success.
